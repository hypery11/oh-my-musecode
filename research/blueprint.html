01Verdict

GO. Start M0 and M1 now.

Twelve follow-up experiments settled the questions that were blocking this. A single bundle ships skills, commands, hooks and working model tools, headlessly, and the experimental gate is needed only at install time. The extension surface did not move across a full minor version — 45 measured axes, two cosmetic differences. Two things are blocked permanently and should be struck rather than deferred: an enterprise tier and MSP-based tool registration.

Muse Code already has the loader. It does not have the ecosystem.

Meta shipped a compiled Rust extension runtime that is better than every oh-my-* loader ever written — a schema-versioned plugin manifest, a validator with 25 typed diagnostic codes, content-addressed package caching, per-capability trust bound to a package digest, two lockfiles, git marketplaces, and native ingestion of Claude Code's and Codex's plugin formats.

And it ships that runtime with no public content, no registry, and effectively no documentation. The muse plugins subsystem has exactly one oblique mention in the entire public documentation corpus. Every published review says no plugin ecosystem, no marketplace and no community catalogue exists. All three exist.

Three facts set the whole design

Cost is measured in tokens

Every extension mechanism ends up as bytes in one POST /responses body. The skills catalog is capped at 32,000 bytes and degrades in three stages — intact, then descriptions dropped tail-first in total silence (skills list --json still reports every skill with empty diagnostics), then entries vanish, which is announced. Stage two is the dangerous one. Meta's own 15 built-ins eat 10,060 bytes of the cap, leaving 21,542 bytes for a bundle.

Trust is the master gate

Project rules, skills, hooks, workflows, agent definitions and plugin installs are all inert until the workspace is trusted. --trust-workspace explicitly does not persist, and there is no muse trust command — only the TUI's first-run prompt writes trust.json. Hand-writing the file works.

Claude's format is now tri-vendor

Muse reads ~/.claude/skills live with no import step, installs .claude-plugin/plugin.json bundles, reads Claude's marketplace.json, honours ${CLAUDE_PLUGIN_ROOT}, and falls back to CLAUDE.md. Author once in the Claude shape and you ship to three agents.

The one thing a roadmap must not promise

The status line and prompt cannot be themed. oh-my-posh is an entire product built on that surface. Muse renders provider · [effort ·] cwd [· YOLO] from compiled code, and no template, format or component key exists anywhere in the 29 settings keys or the 14-field TuiSettings struct.

04Dead ends

Confirmed non-points. Each was actively probed — candidate paths planted with poison files, or fields exercised until they errored. Do not build on these.

  • workspace settingsNo workspace settings file exists. 26 candidate paths planted; none read.
  • plugin autoloadNo auto-discovery of project plugin directories. Valid packages in .agents/plugins, .claude/plugins, .codex/plugins, .muse/plugins and plugins/ were discovered in neither trusted nor untrusted workspaces. Plugins must be explicitly installed.
  • status lineNo statusline, prompt or format key in any of the 29 settings keys or the 14 tui fields.
  • allowed-toolsParsed, canonicalised, recorded — and explicitly not enforced, with a warning-severity diagnostic that says so.
  • enterprise policyEvery execution.* field returns field_not_activated, including forbid_approval_bypass and permission_profiles. An org cannot forbid --yolo today.
  • capabilitiestools, agents, outputStyles, settings and apps are hard unsupported-capability errors in a native manifest.
  • MSP pluginsPlugins are not on the wire. plugin appears 0 times in the exported JSON Schema and 0 times in the TypeScript export.
  • env varsMUSE_HOME, MUSE_CONFIG_DIR, MUSE_SESSIONS and MUSE_NO_SESSION_LOG are not read by the binary. MUSE_SESSIONS is prose inside a bundled skill.
  • plugin data dirMUSE_PLUGIN_DATA_DIR is advertised in the hook environment but the directory is not created. A plugin must mkdir -p it.
  • enterprise tierThe policy plane accepts only documents that express nothing — every field carrying content returns field_not_activated — and the delivery directory cannot be written by anything Meta ships. The defaults plane is live; a restriction cannot be shipped. Strike the team edition from the roadmap.
  • MSP tool registrationMSP has no tool-invocation method and no tool-registration method. An MSP session assembles no run context at all and runs no hooks. The served surface is session/* turn/* model/list view/* approval/* userInput/*. Building a control plane on MSP is not a deferred option, it is a non-option.
  • HOME redirectionRedirecting HOME does not sandbox muse — it composes a session-name-authority path from the real user home via getpwuid and writes there on essentially every run.
The risk no offline check can see

Both builds carry a server-side feature_config provider whose override list includes extensions.skills.allowed_digests, allowed_kinds, extensions.hooks and extensions.runtime_capabilities. Meta can allowlist which skills and extension kinds are permitted without shipping a binary. Pinning a checksum will not catch it. The mechanism is proven; the behaviour needs an authenticated machine to exercise. Design so a rejected extension is detectable — compare what actually composed in a live session against what was written to disk, never disk against disk.

08Recommended shape

oh-my-musecode is a curated content bundle, a thin CLI, and a git marketplace. It is not a loader, and it must never touch the binary.

oh-my-zsh won on five things — zero-friction authoring, a vendored bundle that made the default config already good, a three-line user config, a git-ignored override directory, and an updater that respected the user. It lost on four: no manifest, no registry, no laziness, no namespace management. Muse's runtime already fixes all four losses. The job is to reproduce the five wins on top of it, and add the thing no oh-my-X ever built: per-source cost attribution.

Install tiers — inverted by the experiments

The original plan made the skills-only path the default because the plugin gate looked like user friction. It is not: MUSE_EXPERIMENTAL_PLUGINS=1 is an install-time gate only, proven twice independently. An installed bundle's skills, commands, hooks, MCP servers and agent definitions all compose at session time with the gate unset — so omm sets it on its own subprocess and the user never exports anything.

Four kill switches, all silent at session time

MCP spawn is gated on trusted_enabled. review_needed — the default right after install — trusted_disabled and modified are all skipped with no stderr, no session record and no trace line, while the capability snapshot still reports mcp_servers=N because that field counts declared capabilities. Worse, muse plugins disable deletes the capability line rather than setting a bad status, so a doctor that greps for a bad value sees nothing at all. Any byte change to the package flips everything to modified. omm must own this lifecycle end to end.

Build order

  1. omm doctor + omm cost, standalone

    Zero install footprint, immediate value, and it makes every later decision measurable. It also single-handedly surfaces the silent catalog-drop bug, which nothing else in the ecosystem can do.

  2. Tier 0 install + lint + uninstall + 8–12 skills

    The smallest curated set that is obviously good. Cross-publish to ~/.claude/skills so it lands for Claude Code users too. Ship the uninstaller before the installer.

  3. Lockfile + reconcile + snapshot

    Three-way merge against a recorded ancestor hash. The thing every oh-my-X except fisher and antidote got wrong.

  4. Marketplace + bundle + hooks + MCP servers — pulled forward

    This was gated entirely on "does plugin MCP work". It does, in all three lanes, so it moves up into M1/M2. Reminders, themes and keymaps stay here and are deprioritised.

  5. Skill routing — new, advanced, opt-in only

    skills.v1 is real: negotiation was a missing outputCapabilities field on our side, and read_skill does resolve a routed non-discovered skill by id and by path. But it rides two experimental gates and a per-workspace vendored library, so it can never be a dependency. Build the M1 ledger so this is cheap later; make nothing depend on it.

Fix before anything is published

The plugin id is omm, not oh-my-musecode. Two constraints converge: the model-visible MCP namespace survives verbatim only to 31 characters, forcing len(plugin-id) + len(server-id) ≤ 18; and the plugin id appears twice per catalog entry, so shortening it buys ~22 B per entry — about three extra skills at fifty. What shipped

  • The ledger as the primitive. Install, update, reconcile, doctor and uninstall are one traversal over omm.lock.json. Every settings key carries both its prior value and the value omm wrote, so a user's later hand edit is preserved and named rather than clobbered.
  • Three-way merge from the first release. Update stages a conflict next door and reports it; it never overwrites an edit and never freezes.
  • Plan-then-execute install. Every path is resolved and contained before the first host mutation. A dotfile-manager symlink is refused up front with the flag that skips that category.
  • The trust lifecycle owned end to end. Install approves each capability and verifies the line reads trusted_enabled; update is remove → install → re-approve as one transaction.
  • An in-binary MCP server exposing the doctor and cost reports as tools, proven through a scripted model in both the exec and serve lanes.
  • Opt-in skill routing behind the two experimental gates, with the combined-budget guard.
  • A destructive-command hook that is documented as a heuristic, not a security boundary, and that fails open at the process level while answering deny for the cases it recognises.

Against the seven rival frameworks

A row-by-row parity audit (research/ohmy/01-PARITY.md, 162 distinct capabilities merged from 522 rival rows) answers the natural question honestly: no, omm does not ship everything they ship. 61 rows are HAVE, 39 PARTIAL (the same capability with far less content: no agent roster against their 7–28, 3 commands against 7–77, 3 hooks against 6–56), 36 are buildable gaps, 23 were struck by design (Muse ships subagents and workflows natively; no in-process plugins; no enterprise tier), and 3 are impossible on Muse (statusline, output styles, per-skill tool grants). Nine capabilities appear in omm and in none of the seven: the byte-and-mode-identical uninstall asserted in CI, measured rather than estimated context cost, the host-drift self-test, the doctor that compares a live session against what was installed, the declarative reminder, the launcher shim that refuses prompt smuggling, the offline scripted-model harness, lint through the host's own validators, and ledger-before-write.

Tracking the host

Muse stable moved to 1.0.3-R2198.1 while this was being built. The self-test caught it: one new experimental gate and one new effort value, 33 other axes byte-identical. Host facts now carry a since build tag, so the older pinned build reports the missing gate as OLDER-BUILD rather than a failure, an unlisted gate still fails, and CI runs the gate against both builds. The audit also found a documented hook kill switch that the dispatcher never read — the exact inert-flag pattern the ecosystem survey had criticised in a rival — now enforced and locked by a test.

Not done

11Method

Three orchestrated agent workflows, 74 agents, 15M tokens, 5,669 tool calls.

  • Host teardown. Twelve subsystems, one agent each, working from the shipped aarch64-macos binary — checksum-verified against Meta's release manifest and run in a sandboxed HOME with auto-update disabled. Findings come from running the binary, from Rust panic metadata that leaks the fbsource crate tree, and from string runs read at named file offsets. The TUI could not be driven without a pty that answers its OSC and cursor-position probes, so one was written.
  • Rival teardown. Four discovery lenses — GitHub name patterns, content and topics, package registries, and Chinese-language community sources — produced 134 unique candidates, of which 14 were cloned and read at source level.
  • Verification. Every report was handed to a second agent instructed to refute it: re-run the commands, re-fetch the star counts, re-count the files. Twelve of twelve host dimensions returned mostly solid; none returned shaky. Refuted claims were struck rather than softened, and reconstructed schemas were checked field-by-field against the binary — inventing field names from adjacent string literals is the characteristic failure mode of this kind of work.

Nothing was authenticated, no prompt was sent to Meta's API, and nothing outside a scratch directory was written. Claims are marked proven only where a command reproduces them; everything else is marked inferred and listed under unknowns.
