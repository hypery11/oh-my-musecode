## 3. INSTALL — read end to end

Entry: `bunx oh-my-opencode-slim@latest install`
→ `src/cli/index.ts:main()` → `src/cli/install.ts:runInstall()` (582 lines).

Nine ordered steps, each individually guarded and dry-run-aware:

| # | Step | Writes |
|---|---|---|
| 1 | Check OpenCode present | nothing (`isOpenCodeInstalled()`) |
| 2 | Add plugin to host config | `~/.config/opencode/opencode.json` → `plugin[]` |
| 3 | Add TUI badge | `~/.config/opencode/tui.json` → `plugin[]` |
| 4 | Warm plugin cache | `~/.cache/opencode/packages/oh-my-opencode-slim@<ver>/` + `bun install --ignore-scripts` |
| 5 | Disable host default agents | `opencode.json` → `agent.explore.disable = true`, `agent.general.disable = true` |
| 6 | Enable LSP | `opencode.json` → `lsp = true` **only if the key is absent** (`config-io.ts:632`) |
| 7 | Shell env exports | `~/.zshrc` / `~/.bashrc` / `~/.config/fish/conf.d/opencode-background-subagents.fish` |
| 8 | *(optional)* companion binary | `~/.local/share/opencode/storage/oh-my-opencode-slim/` |
| 9 | Write plugin config | `~/.config/opencode/oh-my-opencode-slim.json` |
| 10 | *(optional)* skill sync | `~/.config/opencode/skills/<8 dirs>` + `~/.config/opencode/.oh-my-opencode-slim/` |

### The writes worth studying

**Atomic write + automatic backup** (`src/cli/config-io.ts:433-452`):
```ts
const tmpPath = `${configPath}.tmp`;
const bakPath = `${configPath}.bak`;
if (existsSync(configPath)) copyFileSync(configPath, bakPath);
writeFileSync(tmpPath, content);
renameSync(tmpPath, configPath);
```
Every host-config mutation goes through this. Good.

**Marker-block shell edit** (`src/cli/background-subagents.ts:10-11, 88-110`):
```
# >>> oh-my-opencode-slim background subagents >>>
export OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true
export OPENCODE_ENABLE_EXA=1
# <<< oh-my-opencode-slim background subagents <<<
```
`upsertBackgroundSubagentsBlock()` finds the markers and replaces between them, so re-running
the installer never duplicates the block. Conda/nvm pattern, executed correctly, with fish
handled as a separate `conf.d` file rather than an rc append.

**Version-pinned, self-identifying plugin entry** (`src/cli/config-io.ts:139-163`):
```ts
return [`${PACKAGE_NAME}@${version}`, { __ohMyOpencodeSlimManagedByInstaller: true }];
```
The marker key (`src/plugin-entry.ts:1`) lets the auto-updater distinguish *"I wrote this
line, I may rewrite it"* from *"the user pinned this by hand, leave it alone"*
(`checker.ts:isInstallerManagedEntry` / `updateInstallerManagedVersions`). This is the
cleanest single idea in the installer.

**Non-destructive by default**: if `oh-my-opencode-slim.json` exists, step 9 prints
`Use --reset to overwrite` and skips (`install.ts:407-419`). `--reset` still `.bak`s first.

### Two things in the installer I would not copy

- **It asks to star the repo and then does it for you** (`install.ts:94-116`): on a TTY it
  prompts, then shells out to `gh api --method PUT /user/starred/alvinunreal/oh-my-opencode-slim`.
  Using the user's authenticated GitHub credential as a growth channel during install is a
  dark pattern. It is opt-in and it fails silently without `gh`, but it should not be in an
  installer at all. This inflates the 8,560-star number by an unknown amount.
- **It rewrites `.jsonc` and eats your comments.** `writeConfig()` warns
  (`config-io.ts:434-437`) — *"Writing to .jsonc file - comments will not be preserved"* — and
  then does it anyway, via `JSON.stringify`. Meanwhile the *reader* has a full JSONC tokenizer
  (`checker.ts:tokenizeJsonc`, ~50 lines) used for surgical version-string patching. The
  capability exists on the read path and is not wired into the write path.

## 4. EXTENSION CONTRACT — how a user extends without forking

This is the strongest part of the design, and there are **four distinct layers**, none of
which require touching the repo.

### (a) Layered config with a documented precedence chain

`docs/project-local-customization.md` + `src/config/loader.ts:loadPluginConfig()`:

```
Built-in defaults
  → ~/.config/opencode/oh-my-opencode-slim.json[c]        (user)
  → <project>/.opencode/oh-my-opencode-slim.json[c]        (project)
  → $OH_MY_OPENCODE_SLIM_PRESET                            (env override)
  → active preset merged into agents
  → root agents.* (beats preset)
```

`deepMerge()` (`loader.ts:617-651`) recurses objects, replaces arrays and primitives. The
precedence is written down *and* tested (`src/config/project-local-customization.test.ts`,
`loader.test.ts`).

### (b) Custom agents as unknown config keys

`src/agents/index.ts:563-604` — any key under `agents.` that is not a built-in name becomes a
new subagent. Requirements: a `model` (or `inheritModelFrom`), a name passing
`isSafeCustomAgentName()`. No file, no registration, no plugin API.

The clever bit is `orchestratorPrompt`: a custom agent supplies a snippet that gets injected
into the *orchestrator's* prompt under `# Project-specific routing guidance`
(`src/agents/index.ts:747-748`). So adding an agent also teaches the router when to call it —
routing is part of the extension declaration, not a separate edit. The schema explicitly
rejects `agents.orchestrator.orchestratorPrompt` to prevent recursion
(`src/config/schema.ts:424-436`).

### (c) Filesystem prompt overrides with a 4-level search path

`src/config/loader.ts:767-851` (`loadAgentPrompt`):

```
1. <project>/.opencode/oh-my-opencode-slim/<preset>/<agent>.md
2. <project>/.opencode/oh-my-opencode-slim/<agent>.md
3. <user-config>/oh-my-opencode-slim/<preset>/<agent>.md
4. <user-config>/oh-my-opencode-slim/<agent>.md
```

For every agent, two independently-resolved files: `<agent>.md` **replaces** the built-in
prompt, `<agent>_append.md` **appends** to whatever base won. Final composition:
`effectiveBase = inlinePrompt ?? filePrompt ?? builtIn`, then `+ "\n\n" + appendPrompt`.

The **append** channel is the load-bearing idea. Most frameworks give you replace-only, which
forces a user who wants to add one rule to fork the whole prompt and then eat every upstream
prompt improvement by hand. `_append.md` lets a user add a house rule and keep receiving
upstream prompt updates forever. Steal this.

When both inline and file prompts exist, it warns rather than silently picking
(`docs/project-local-customization.md`, "Conflict warning").

### (d) The framework ships a skill that configures the framework

`src/skills/oh-my-opencode-slim/SKILL.md`:
> *"You help users configure, customize, and safely improve their oh-my-opencode-slim setup…
> Also use it proactively, with restraint, when a session reveals a repeatable improvement
> opportunity."*

And `src/skills/reflect/SKILL.md` closes the loop — it reads the host's session SQLite DB
(`~/.local/share/opencode/opencode.db`) to mine repeated friction, then recommends
"a skill, custom agent, command, configuration change, prompt rule, documentation playbook,
or no change."

This is the genuinely novel extension contract: **the documentation is executable by the
agent that will do the extending.** The user does not read `configuration.md`; the user says
"make my setup better" and the orchestrator activates a skill that knows the config schema.
For a system whose users all have a coding agent in the terminal, this beats a plugin API.

### What is NOT extensible

- **Skills.** There is no user-skill mechanism *in this framework*. `~/.config/opencode/skills/`
  belongs to OpenCode; the plugin only issues **permission grants** via `agents.<n>.skills`
  (`src/cli/skills.ts:33-88`, supporting `"*"`, explicit names, and `"!name"` deny). This is
  actually correct layering — host owns discovery, framework owns authorization — but it means
  "add your own skill" is a host feature, not a slim feature.
- **Hooks, tools, MCPs.** Fixed sets, compiled in. A user can only `disabled_hooks`-style
  subtract (`disabled_mcps`, `disabled_tools`, `disabled_skills`, `disabled_agents`). No
  third-party tool or MCP can be added through the plugin config.
- **ACP agents** (`acpAgents` in schema) are the one escape hatch: spawn an arbitrary
  external agent binary as a subagent, with `command`/`args`/`env`/`permissionMode`.

## 5. UPDATE — and the anti-clobber machinery

Two independent update paths.

### Plugin self-update

`src/hooks/auto-update-checker/index.ts` fires once per top-level `session.created`, in
`setTimeout(0)` so it never blocks startup. Then:

1. Skip entirely if running from a local dev checkout (`getLocalDevVersion`).
2. Fetch `registry.npmjs.org/-/package/oh-my-opencode-slim/dist-tags`, 5s timeout.
3. Channel-aware: extracts `beta`/`latest` from the current version (`extractChannel`).
4. **Refuses to cross a major version.** `blockedByMajor` → toast only, no install.
5. **Refuses if the user pinned the version by hand** (`pluginInfo.isPinned` and not
   installer-managed) → toast only.
6. Stage → verify → publish: `preparePackageUpdate()` into a staging dir,
   `runBunInstallSafe()` (300s timeout, kills the process on overrun),
   `verifyInstalledPackage()` checks the resulting package.json version, and only then
   `publishPackageUpdate()`. On any failure, `discardPreparedPackageUpdate()`.
7. If the config line is installer-managed, patch the pinned version *in place in the JSONC*
   using the tokenizer, preserving comments.

### Skill sync — the piece worth stealing wholesale

`src/hooks/auto-update-checker/skill-sync.ts` (1,322 LOC source, 1,782 LOC of tests).
This is a **three-way merge for config assets**, and it is the best-engineered thing in the repo.

State lives in `~/.config/opencode/.oh-my-opencode-slim/skills-manifest.json`:

```ts
interface SkillManifestEntry {
  status: 'managed' | 'customized' | 'deleted' | 'conflict';
  packageVersion: string;
  sourceHash: string;        // hash of what the package ships now
  lastManagedHash: string;   // hash of what WE last wrote
  lastSeenHash: string;      // hash of what is on disk
  stagedPath?: string;
  updatedAt: string;
}
```

`computeDirectoryHash()` (line 141) is a deterministic SHA-256 over sorted relative paths,
file kinds and modes, explicitly **skipping symlinks** (`lstatSync` + `isSymbolicLink()`
continue). The decision table (lines ~925-1000):

| on-disk hash | vs `lastManagedHash` | vs `sourceHash` | action |
|---|---|---|---|
| = lastManaged | — | = source | no-op, refresh manifest |
| = lastManaged | — | ≠ source | **overwrite** (user never touched it) |
| ≠ lastManaged | user edited | = source | **adopt** — user converged on our version |
| ≠ lastManaged | user edited | ≠ source | **stage, do not touch** → `status: 'customized'` |
| missing | — | — | `status: 'deleted'`, never reinstall |

A staged update lands in
`~/.config/opencode/.oh-my-opencode-slim/skill-updates/<version>/<skill>/` and the user gets a
toast naming exactly which skills need review.

Supporting details that show real operational thinking:

- **Cross-process lock** at `.oh-my-opencode-slim/skills.lock` (mkdir-based), with a 5-minute
  staleness expiry (`CROSS_HOST_LOCK_EXPIRY_MS`) and a per-process UUID token so a process
  can recognise its own stale lock.
- **Fail-closed on manifest corruption**: `validateManifest()` is a full structural check; if
  it fails, `isManifestCorrupt = true` and existing skills are skipped rather than overwritten
  (`skill-sync.ts:651-665, 795`).
- **Crash recovery**: `recoverOrphanArtifacts()` cleans half-finished `.bak`/staging dirs from
  an interrupted run before deciding anything.
- **Path-confinement on delete**: `removeManagedStagedPath()` (line 513) resolves the path and
  refuses to `rmSync` anything not under `<manifestDir>/skill-updates`, logging
  *"Refusing to delete staged path… is not under managed root."*
- **Escape hatch**: `install --skills=force` discards local customizations deliberately.
- **`LEGACY_MANAGED_SKILL_HASHES`** (line 84) — a documented (currently empty) table of hashes
  of historically-shipped skill versions, so users who never edited an old version can be
  auto-adopted rather than being told they have a conflict. The comment includes the
  `npm pack` recipe for populating it. Forward-thinking; nobody has done the work yet.

### Companion binary update

`src/companion/updater.ts` — pinned manifest (`COMPANION_MANIFEST`, version 0.1.3) with
**SHA-256 per platform archive**, downloaded from GitHub releases, verified before extraction
(`updater.ts:238-278`), install metadata recorded, lock with 2s acquire / 5-min staleness.

## 9. What is GOOD and what is BAD

### Good — and specifically worth stealing

1. **The three-way skill merge.** `skill-sync.ts` is the answer to "how does a framework
   update shipped assets a user may have edited." `lastManagedHash` is the ancestor,
   `sourceHash` is theirs, on-disk is yours. Four outcomes, all correct, all tested. The
   *staging* behaviour (write the new version next door and toast about it) is exactly right:
   never overwrite, never silently skip forever.
2. **`_append.md`.** Two independent override channels — replace and append — resolved
   separately across a 4-level search path. Append is what keeps users from forking prompts.
3. **The installer-managed marker key.** `{ __ohMyOpencodeSlimManagedByInstaller: true }`
   in the host's own config array. One boolean that distinguishes "my line" from "the user's
   line" and thereby makes auto-update safe. Cheap and load-bearing.
4. **Marker-block shell edits** with fish routed to `conf.d` instead of an rc append.
5. **Init health check.** `src/health-check.ts` asserts minimum agent/tool/MCP counts at
   plugin init and *tells the user which dependency probably failed*, with an issue link.
   Frameworks fail silently by loading empty; this one refuses to.
   Bonus: the file's header comment documents why it is deliberately not re-exported from the
   package root (OpenCode's legacy loader invokes every named export as a plugin factory) —
   a real bug (#894) turned into a permanent structural guard.
6. **`doctor --json`.** Validates user *and* project config against the Zod schema, normalises
   `disabled_*` keys the same way the loader does so diagnostics match runtime, and prints
   `z.prettifyError` output.
7. **Generated JSON Schema + `$schema` URL in the emitted config.** Editor autocomplete on a
   1,435-line schema, generated from the Zod source so it cannot drift.
8. **34 `codemap.md` files**, one per source directory, plus a machine-readable
   `.slim/codemap.json` with per-file hashes. The repo maintains a navigation index *for the
   agents working on it*. Dogfooding its own `codemap` skill.
9. **1.25:1 test-to-source ratio**, with the riskiest module (skill-sync) carrying more test

1. **No uninstall, and the manual doc is already wrong** (7 skills listed, 8 installed) and

## 10. Transfer to Muse Code (compiled Rust binary host)

### Transfers directly — port these

| Pattern | Source | Muse Code shape |
|---|---|---|
| **Three-way asset merge** (`managed`/`customized`/`deleted`/`conflict` + `lastManagedHash`) | `skill-sync.ts` | This is what `.muse/skills.lock` should hold. Muse already has a lock file for skills; give it the ancestor hash, not just a version, and you get non-clobbering updates for free. Directory SHA-256 over sorted (relpath, kind, mode), symlinks skipped, is ~40 lines of Rust. |
| **Staging directory for conflicting updates** + a notification naming the conflicts | `.oh-my-opencode-slim/skill-updates/<version>/<skill>/` | `~/.config/muse/.oh-my-musecode/updates/<version>/<asset>/`. Never overwrite; stage and tell. |
| **`<agent>.md` replace + `<agent>_append.md` append**, resolved independently over a 4-level search path | `loader.ts:767-851` | Maps onto Muse's rules/agent-definitions subsystems as-is. The append channel is the single highest-value idea to carry over. |
| **Installer-managed marker in the host's own config** | `__ohMyOpencodeSlimManagedByInstaller` | A `"managed_by": "oh-my-musecode"` field on entries oh-my-musecode writes into `.muse-plugin/plugin.json` or `.muse/hooks.json`. Makes update and uninstall both safe and precise. |

| **Path-confinement before any recursive delete** | `removeManagedStagedPath()` | `canonicalize()` + `starts_with(managed_root)` before `remove_dir_all`. Non-negotiable for a tool that deletes directories. |
| **Marker-block shell edits** for env exports | `background-subagents.ts` | Muse Code's ~45 `MUSE_EXPERIMENTAL_*` gates are exactly the case that needs this. `# >>> oh-my-musecode >>>` … `# <<<`, upsert between markers, fish to `conf.d`. |
| **Atomic write + `.bak`** on every host-config mutation | `config-io.ts:433-452` | `tempfile` + `persist()`. Trivial and mandatory. |
| **Pinned manifest with per-platform SHA-256** for binary artifacts | `companion/updater.ts` + `companion-manifest.json` | Directly applicable to distributing an oh-my-musecode Rust binary. Copy the companion, not the ast-grep downloader. |

### Does NOT transfer

- **The npm/bunx delivery model.** `bunx oh-my-opencode-slim@latest install`, the
  `~/.cache/opencode/packages/…` warm-up, `bun install --ignore-scripts`, `dist-tags`
  channel detection — all of it assumes a JS package manager on the host and a host that
  loads plugins by resolving node modules. Muse Code is a compiled binary. Distribution has to
  be a released artifact (GitHub releases + checksums, brew, cargo-binstall) or a plain
  `git clone` of declarative assets. **Choose one before designing anything else**, because
  every update and uninstall decision follows from it.
- **In-process plugin architecture.** 53k lines of TypeScript running inside the host process,
  wrapping the host's tools, mutating the host's in-memory config object via a `config` hook,
  registering tool implementations. Muse Code will not load a TS plugin into its address space.
  Muse's surface is `.muse-plugin/plugin.json` manifests, `.muse/hooks.json`, and the MSP stdio
  host — meaning oh-my-musecode is either **(a)** a pure asset+config bundle with subprocess
  hooks, or **(b)** an MSP server speaking the session protocol. It cannot be (c) "a plugin
  that is really a program inside Muse."
- **Everything that depends on JS runtime introspection**: `fileURLToPath(new URL('../..'))`
  for package root, reading `process.argv[1]` to detect whether you are a dev checkout or an
  npm install, `import.meta.main`. A Rust binary knows where it is.
- **The TUI sidebar** (`@opentui/solid` + `solid-js`) and the JS webfetch stack
  (jsdom + `@mozilla/readability` + turndown). If Muse Code needs enriched fetch, it is a Rust
  crate or an MSP server, not a bundled DOM.
- **The `gh` CLI dependency** in the installer (both the star prompt and any GitHub calls).
  A Rust installer should not shell out to `gh`.
- **The "disable the host's built-in agents" move** (`agent.explore.disable = true`). This is
  a specific OpenCode affordance. Muse's `.muse/lock.json` has `allowed_tools` and quarantine
  semantics that are a *different and probably better* mechanism — use those, do not replicate
  a boolean-disable pattern.
- **`OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS` as an architectural dependency.** The lesson
  transfers as a warning, not a pattern: do not build oh-my-musecode's core value on one of the
  45 `MUSE_EXPERIMENTAL_*` gates, or you inherit that flag's stability and its support burden.
- **The npm-registry-polling auto-updater.** Replace with signed release artifacts + checksum
  manifest (the companion updater is the in-repo model, not the plugin updater).
- **The "slim" name-as-wedge play.** It worked here because there was a 68k-star maximalist
  incumbent to be slim *against*. Muse Code is brand new with no incumbent OMM framework.
  There is nothing to counter-position against yet, so the growth play does not port — only
  the engineering does.

### The one strategic read

The highest-leverage thing in this repo is not any single mechanism — it is that
`skill-sync.ts` treats shipped config assets **as a version-controlled merge problem with a
recorded common ancestor**, and that `_append.md` gives users a way to customise that never
creates a merge in the first place. Together they solve the actual failure mode of every
oh-my-* framework: *"I edited a file and now I can never update again."*

Build `.muse/skills.lock` and the oh-my-musecode manifest around `lastManagedHash` from day
one. Retrofitting an ancestor hash after users already have edited files on disk is the
problem `LEGACY_MANAGED_SKILL_HASHES` exists to solve — and note that in this repo, that
table is still empty.
